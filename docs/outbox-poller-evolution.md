# Outbox 폴러 발전 과정 (V1 → V2 → V3)

미션 완료 로그를 API 서버에서 Admin 서버로 전달하는 Outbox 재시도 폴러가
세 번의 구조 변경을 거친 이유와 각 단계의 트레이드오프를 정리한다.

## 배경: 이 컴포넌트가 하는 일

```
미션 완료 (@Transactional)
 ├─ 완료 기록 저장
 └─ OutboxEvent 저장          ← 같은 트랜잭션 (원자성 보장)
        │
        ├─ [Happy Path] AFTER_COMMIT 이벤트 리스너가 비동기로 Admin API 호출 → 성공 시 Outbox 삭제
        └─ [Fallback]   리스너가 실패하면 Outbox에 행이 남음 → 폴러가 주기적으로 재전송
```

- 폴러는 **at-least-once** 전달을 책임진다. "정확히 한 번"은 수신자(Admin)의
  멱등키 + UNIQUE 제약이 만든다. (전송 성공 후 응답 유실 → 재전송이 항상 가능하므로)
- 전제 조건: **인스턴스 2대**가 같은 폴러를 스케줄로 돌린다. 즉 "같은 이벤트를
  두 인스턴스가 동시에 집는 것"을 어떻게 막느냐가 전 버전을 관통하는 설계 문제다.

### 관통하는 문제의식

> 이벤트를 "집는 행위(claim)"와 "처리 완료" 사이에 외부 API 호출이라는
> 긴 시간이 끼어 있다. 이 틈 동안 다른 폴러가 같은 이벤트를 집지 못하게 하는
> 장치가 필요한데, 그 장치가 무엇이냐에 따라 버전이 갈린다.

| 버전 | claim 장치 | 대가 |
|------|-----------|------|
| V1 | DB row 락 (트랜잭션 유지) | 외부 호출 동안 커넥션 점유 |
| V2 | PROCESSING 상태 커밋 | 고아 상태 복구용 timeout 스케줄러 필요 |
| V3 | Redis SPOP의 원자성 | Redis 의존 추가 |

## V1: 단일 트랜잭션 (`OutboxPoller` + `PollProcesser`)

### 구조

```
@Scheduled(30s)
@Transactional  ─────────────────────────────────┐
  1. READY 이벤트 조회 (SELECT ... SKIP LOCKED)   │ 하나의
  2. 건별로 Admin API 호출 (timeout 3s)           │ 트랜잭션
  3. 성공/영구실패 건 삭제                         │ = 커넥션 1개 점유
─────────────────────────────────────────────────┘
```

- 동시성 제어는 `SKIP LOCKED`가 해결: 인스턴스 A가 잡은 행을 B는 건너뛰고
  다른 행을 가져간다. 트랜잭션이 살아있는 동안 row 락이 곧 claim이다.

### 무엇이 문제였나

**외부 API 호출이 트랜잭션 안에 있다** → 호출 시간만큼 커넥션을 점유한다.
Admin이 정상일 땐 티가 안 나지만, **Admin 장애 시 최악 시나리오**:

- 초당 완료 요청 1건 가정 → Admin이 죽어 있는 1분 동안 Outbox에 60건 적재
- batch 30건 × timeout 3초 = **한 사이클에 커넥션을 최대 90초 점유**
- 스케줄 주기(60초) < 처리 시간(90초) → 사이클이 겹치며 커넥션 2개가
  거의 상시 점유 상태
- Admin이 죽어 있는 내내 이 점유가 반복 → **Admin 장애가 API 서버의
  커넥션 풀 고갈로 전이**될 수 있는 구조

핵심 결함: **외부 시스템의 응답 시간이 우리 DB 자원 점유 시간을 결정한다.**

## V2: 트랜잭션 분리 + PROCESSING 상태 (`OutboxPollerV2` + `OutboxTransactionManager`)

### 개선 목표

외부 API 호출을 트랜잭션 밖으로 꺼내 커넥션 점유를 없앤다.

### 구조

```
Tx1 (짧음): READY 조회 (SKIP LOCKED) + PROCESSING으로 변경 + 커밋
   ↓
(트랜잭션 없음): 건별 Admin API 호출        ← 커넥션 미점유
   ↓
Tx2 (짧음): 성공/영구실패 → 삭제, 일시실패 → READY로 복귀
```

### 왜 PROCESSING 상태를 "커밋"까지 해야 했나

트랜잭션을 쪼개는 순간 **V1의 claim(row 락)이 사라진다.** Tx1이 커밋되면
락이 풀리므로, API 호출 중인 수십 초 동안 그 이벤트는 다른 폴러 눈에
"아무도 안 집은 이벤트"로 보인다. 그러면:

- 다른 인스턴스의 폴러가 같은 이벤트를 또 전송
- 처리(최대 90초)가 주기(60초)보다 길어지면 같은 인스턴스의 다음 사이클도 중복 픽업

Admin의 멱등키가 데이터는 지켜주지만, 죽어 있는 Admin에 중복 트래픽을
증폭시키고 batch 슬롯을 낭비한다. 그래서 **락을 대신할 영속적인 claim**으로
PROCESSING 상태를 두었고, 다른 트랜잭션 눈에 보여야 하므로 호출 **전에
커밋**해야 한다. (커밋 안 하면 격리 때문에 남들은 여전히 READY로 읽는다)

### 무엇이 문제였나

**claim에 만료가 없다.** PROCESSING 커밋 직후 어떤 실패가 나든 이벤트가
PROCESSING에 갇힌다:

1. Tx1 커밋 직후 서버 다운 → 호출도 못 하고 PROCESSING 고아
2. API는 성공했지만 Tx2 삭제 실패 → PROCESSING 고아
3. 알 수 없는 예외 → PROCESSING 고아

되돌릴 주체가 없으므로 **별도 복구 스케줄러**(`recoverStuckProcessing`)가
필요했다: "updatedAt이 90초(= batch 30 × timeout 3초, 정상 처리의 상한)보다
오래된 PROCESSING은 죽은 것으로 간주하고 READY로 되돌린다."

이 복구의 약점:

- **추정 기반이다.** "90초 지났으면 죽었다"는 판정은 실제로 아직 처리 중인
  이벤트를 되돌릴 수도 있다 (그 순간 중복 전송).
- **설정에 결합된 상수다.** batch 크기나 timeout을 바꾸면 90초 기준도 함께
  갱신해야 하는데, 이 연결이 코드에 암묵적으로만 존재한다.
- 폴러 + 복구 스케줄러 + 상태 전이 규칙을 모두 알아야 동작을 이해할 수 있어
  **유지보수 난도가 높다.**

## V3: Redis SET 작업 큐 (`OutboxPollerV3` + `OutboxProducer` + `OutboxConsumer`)

### 개선 목표

"처리 중"이라는 **중간 상태를 DB에 남기지 않는다.** 상태가 없으면 고아도
없고, timeout 추정 복구도 필요 없다.

### 구조

```
@Scheduled(60s) — 모든 인스턴스에서 실행

[1. 장전 - Producer]
  분산락 tryLock ── 성공한 1대만 ──> DB에서 미발행 이벤트 조회
                                     → Redis SET에 SADD (이벤트 ID)
  락 실패 인스턴스 ──> RCountDownLatch로 장전 완료까지 대기

[2. 소비 - Consumer]  ← 모든 인스턴스가 동시 진입
  while (true):
      id = SPOP(outbox:set:queue)   ← 원자적: 하나의 이벤트는 정확히 1대만 획득
      if id == null: break
      Admin API 호출 (트랜잭션 없음)
      성공/영구실패 → Outbox 행 삭제
      일시실패     → 아무것도 안 함 (행이 남아 다음 장전에서 재적재)
```

### 설계 포인트

- **claim = SPOP의 원자성.** "꺼내는 행위"가 곧 소유권 획득이라, DB에
  아무 상태도 남기지 않고 중복 픽업이 차단된다. V2가 상태 커밋으로 풀던
  문제를 자료구조의 성질로 대체한 것.
- **SET을 쓴 이유(중복 적재 방어):** 이전 사이클의 소비가 끝나기 전에 락이
  풀려 다음 장전이 실행되면, 아직 삭제 안 된 이벤트가 다시 적재될 수 있다.
  LIST였으면 같은 ID가 두 번 들어가 두 인스턴스가 중복 처리하지만, SET은
  SADD가 자연스럽게 멱등이라 한 번만 존재한다.
- **CountDownLatch 동기화:** 락을 못 잡은 인스턴스가 장전 완료 전에
  Consumer로 진입하면 빈 SET을 보고 그냥 종료해버린다(그 사이클의 병렬성
  상실). Redisson `RCountDownLatch`로 전 인스턴스가 장전 완료 후 **동시에**
  소비를 시작하게 했다. (Producer 예외 시에도 finally에서 countDown하여
  대기 인스턴스가 영원히 잠들지 않게 처리)
- **실패 처리의 단순화:** 일시 실패 시 "READY로 되돌리는" 작업 자체가 없다.
  Outbox 행은 성공했을 때만 삭제되므로, 실패 건은 가만히 있어도 다음 장전
  대상이다. 복구 로직이 "없는 것"이 V3의 복구 전략이다.

### 남아 있는 트레이드오프 (정직한 한계)

- **Redis 의존 추가.** Redis 장애 시 폴링이 멈춘다. 단, 이벤트는 Outbox
  테이블에 계속 쌓이므로 유실은 없고, Redis 복구 후 재개된다. (전달 지연은
  발생)
- **SPOP 후 인스턴스가 죽으면** 그 이벤트는 해당 사이클에서 처리되지 않는다.
  하지만 Outbox 행이 살아 있으므로 다음 장전에서 재적재된다 — at-least-once
  유지. 중복 전송 가능성은 Admin의 멱등키가 최종 방어한다.
- **처리 순서 보장 없음.** SET은 순서가 없다. 미션 로그 집계는 순서에
  민감하지 않아 문제없지만, 순서가 필요한 이벤트에는 이 구조를 그대로 쓸 수 없다.

## 요약 비교

| | V1 | V2 | V3 |
|---|---|---|---|
| 구조 | 조회+호출+삭제 단일 Tx | Tx1(claim) / 호출 / Tx2(정리) | Redis 큐 장전 / SPOP 소비 |
| 중복 픽업 방지 | row 락 (SKIP LOCKED) | PROCESSING 상태 커밋 | SPOP 원자성 + SET 멱등 적재 |
| 호출 중 커넥션 | **점유 (최대 90초)** | 미점유 | 미점유 |
| 중간 상태 | 없음 | **PROCESSING (고아 가능)** | 없음 |
| 복구 로직 | 불필요 | **timeout 추정 스케줄러 필요** | 불필요 (미삭제 행 = 재시도 대상) |
| 수평 확장 | batch 분할에 의존 | batch 분할에 의존 | 인스턴스 수만큼 자동 분배 |
| 추가 의존성 | - | - | Redis (Redisson) |

## 한 줄 정리

> V1은 트랜잭션 락으로 claim을 해결했지만 외부 호출이 커넥션을 인질로 잡았고,
> V2는 커넥션을 풀어주는 대신 claim을 DB 상태로 옮기며 "만료 없는 claim"이라는
> 새 문제(timeout 추정 복구)를 만들었다. V3는 claim을 Redis SPOP의 원자성으로
> 옮겨 중간 상태 자체를 제거했다 — 상태가 없으니 고아도, 추정 복구도 없다.
